# Azure SRE Agent 실습 가이드 (Zava AKS + PostgreSQL) 설계

- 작성일: 2026-11-24
- 상태: 승인 대기

## 1. 의도와 배경

팀 내부 학습용 가이드를 만든다. 기반은 Microsoft 공식 저장소 `microsoft/sre-agent`의 `labs/zava-aks-postgres` 랩이다. 목표는 **처음 보는 팀원도 혼자 끝까지 따라 할 수 있는 한국어 step-by-step 가이드**다.

가이드는 명령만 나열하지 않는다. 단계마다 무엇을 하는지, 무엇이 보여야 하는지, 왜 그렇게 동작하는지를 설명한다. 이를 통해 팀원이 SRE Agent의 동작 원리를 이해하게 한다. 다룰 개념은 Response plan, Skill, Custom agent, Hook, VNet 주입, Run mode다.

가이드는 실제 Azure 구독에서 **직접 수행해 검증**한다. 순서는 배포, 시나리오 1~5 실행, 정리다. 검증하며 관찰한 결과도 가이드에 반영한다. 관찰 결과에는 에이전트 응답 요약, 소요 시간, 실제로 겪은 이슈가 포함된다.

## 2. 목표 / 비목표 / 안티목표

**목표**
- 사전 준비부터 배포, 동작 확인, 시나리오 1~5, 정리까지 단계별 한국어 가이드를 작성한다.
- 단계마다 실행 명령, 기대 결과, 확인 위치(포털 메뉴 경로), 학습 포인트, 문제 해결 방법을 넣는다.
- 랩 코드를 이 저장소에 복사(vendoring)한다. 원본이 바뀌어도 같은 결과를 재현할 수 있게 하기 위해서다.
- 실제 실행 검증 결과를 가이드에 수록한다.

**비목표**
- 랩 아키텍처나 IaC의 기능 변경 또는 단순화
- 고객 워크숍용 슬라이드나 블로그 문체
- 프로덕션 도입 설계 가이드

**안티목표 (기술적으로 돌아가도 실패로 간주)**
- 검증하지 않은 명령이나 화면 설명을 "확인된 것"처럼 쓴 가이드
- 테스트 후 Azure 리소스가 남아 비용이 계속 발생하는 상황
- 원본 랩의 의도를 깨는 수정. 원본은 정답을 에이전트에게 숨기고, 알림 설명에는 증상만 적는다.

## 3. 제약

- **구독:** 작성자의 개인 실습 구독이다(az 로그인 완료, 이름은 기록하지 않음). 구독 범위에 Owner 또는 User Access Administrator 권한이 필요하다.
- **리전:** `swedencentral`을 쓴다(원본 AGENTS.md 권장).
- **도구:** `az`, `azd`(1.37.2 확인), `pwsh`가 필요하다. AKS가 Private 클러스터라 운영자 PC에는 `kubectl`이 필요 없다. 클러스터 작업은 `az aks command invoke`로 한다.
- **소요 시간:** 배포에 약 25분 걸린다. 알림 평가 주기(PT5M)에 조사 시간이 더해져 시나리오당 10~20분이 예상된다.
- **비용:** Azure Firewall, AKS, PostgreSQL이 포함되어 비용이 크다. 테스트 직후 `azd down --force --purge`를 반드시 실행한다.
- **라이선스:** 원본은 MIT 라이선스다. 저작권 고지와 LICENSE 파일을 반드시 유지한다.
- **태그:** 구독 정책이 owner나 expiry 같은 태그를 요구하면 리소스 그룹에 즉시 부여한다.

## 4. 접근 방식 (검토한 대안)

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 원본 참조 | 가이드만 작성하고, 실습할 때 원본을 clone한다(커밋 고정). | 가볍고 원본 업데이트를 따라가기 쉽다. | 원본 구조가 바뀌면 가이드를 수정해야 한다. |
| **B. 코드 복사 (선택)** | 원본 랩을 이 저장소에 복사하고, 가이드는 복사본을 기준으로 쓴다. | 원본이 바뀌어도 안정적으로 재현된다. | 코드가 중복되고, 라이선스 고지와 업데이트 추적이 번거롭다. |
| C. 자체 단순화 랩 | Firewall을 빼는 등 IaC를 새로 작성한다. | 비용과 시간이 줄어든다. | 작업량이 크고, 검증된 구성의 학습 가치를 잃는다. |

사용자가 **B**를 선택했다.

### 5.3 가이드 페이지 공통 형식
1. **목표:** 이 단계에서 하는 일을 2~3줄로 설명한다.
2. **소요 시간과 비용 메모**
3. **단계별 절차:** `Step N`마다 다음을 적는다.
   - 실행 명령(PowerShell 코드 블록)
   - **기대 결과**
   - **확인 방법**(포털 메뉴 경로 또는 명령)
4. 💡 **학습 포인트:** 왜 이렇게 동작하는지 설명하고, 관련 설정 파일 경로를 링크한다.
5. ⚠️ **자주 겪는 문제**
6. ✅ **체크리스트:** 다음 단계로 넘어가기 전에 확인할 항목

시나리오 페이지는 다음 흐름을 추가로 따른다.
1. 장애를 주입한다.
2. 알림 발생을 확인한다.
3. 에이전트의 조사 과정에서 관찰할 포인트를 짚는다.
4. 실제 검증 때 나온 에이전트 결론 요약과 소요 시간을 적는다.
5. fix 스크립트로 복구한다.
6. 알림이 Resolved 상태가 될 때까지 기다린다.

### 5.4 테스트(검증) 범위
- 실제 구독에서 가이드 절차대로 배포한다.
- 스토어프론트가 정상 동작하는지 확인한다.
- 시나리오 1~5를 모두 실행하고, 시나리오마다 알림 발생, 에이전트 조사, 복구 결과를 기록한다.
- 다음 시나리오로 넘어가기 전에 알림의 `monitorCondition`이 `Resolved`인지 확인한다(원본 지침).
- 마지막에 `azd down --force --purge`를 실행하고, 잔여 리소스를 확인한다. 구독 범위 역할 할당도 확인 대상에 포함한다.
- 검증 결과는 각 시나리오 페이지의 "실제 실행 결과" 섹션과 `guide/10-troubleshooting.md`에 반영한다.

### 5.5 사용 환경과 검증 기준
- **사용 환경:** 팀원은 **각자 자기 구독**을 쓴다(사용자 답변). 가이드에는 구독 ID, 이름, 이메일 같은 개인 값을 넣지 않고 `<구독 ID>` 같은 placeholder로 쓴다. 공유 구독 시나리오는 다루지 않는다.
- **랩 코드를 수정하는 경우:** 수정한 부분의 영향을 받는 단계만 다시 검증한다. *(빌더 판단)*
- **에이전트가 오진하거나, 복구에 실패하거나, 알림이 발생하지 않는 경우:** 1회 재시도한다. 그래도 같으면 관찰한 그대로 "실제 실행 결과"에 기록하고 다음 단계로 넘어간다. 실패한 실행도 학습 자료로 쓸 수 있다. *(빌더 판단)*

### 5.6 문체
- 한국어로 쓰고, 팀원 대상 존댓말("~합니다")을 쓴다. 영어 기술 용어는 원어를 유지한다.
- 표 안의 `|`는 `\|`로 이스케이프한다.

## 6. 빌더에게 맡기는 판단
- 각 페이지의 분량과 세부 문구
- 포털 화면 캡처 포함 여부. 가능하면 텍스트로 쓴 메뉴 경로를 우선한다.
- 에이전트 응답은 실행할 때마다 달라질 수 있다. 그래서 결과는 "예시 결과"로 표기하고, 관찰 포인트를 중심으로 서술한다.
- 배포가 실패하면 원인을 분석해, 최소 수정을 할지 재시도할지 판단한다.
